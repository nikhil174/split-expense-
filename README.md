# Split It

Mobile-first expense sharing for a group, hosted on Cloudflare Workers + D1.

## Accounts, groups and admins (migration `0013`)
- **One account per person**, in any number of groups (`appx_users`). Sign up with a name, a unique **username** (3–30 letters, numbers, `_` or `.`, starting with a letter; case-insensitive), an optional unique **email**, and a **password** (8–128 characters with letters and numbers). Sign in with username *or* email + password (`POST /api/auth/signup`, `/api/auth/signin`; `GET /api/auth/username?u=` checks availability). People from before passwords keep their **4-digit PIN as their password**. Sessions (`split_user` cookie, `appx_user_sessions`) last 30 days.
- **Sign in with Google** (`POST /api/auth/google`): Google Identity Services gives the app an ID token; the Worker checks its RS256 signature against Google's published keys (cached), and `iss`, `aud = GOOGLE_CLIENT_ID`, `exp` and a verified email. A new Google account creates a Split It account (no password until added in Profile). An email already on a password account is **not** taken over: its owner signs in with the password and connects Google in Profile (`POST /api/me/google`, `/api/me/google/disconnect`, which needs a password). **Off until the Worker variable `GOOGLE_CLIENT_ID` is set**; the button is hidden until then.
- **Group PINs** (migration `0015`): every new group has a 4-digit PIN, needed to **join** it (accepting an invitation) and to **open** it. Opening is remembered for **1 day** per signed-in device (`appx_group_unlocks`); until then every `/api/groups/:id/*` route answers `423 group_locked`. 5 wrong PINs lock that group for that person for 15 minutes. Admins set or change it (Members → Group PIN, `POST …/pin`); everyone else then needs the new one and is notified. Groups from before PINs open freely until an admin sets one. Signing out forgets what that device had open.
- **Profile** (`#/profile`, `POST /api/me/profile`, `/api/me/password`): change name (shown everywhere, past expenses too), username, email and password (needs the current one), and connect Google. UPI details belong to the account and show in every group.
- **Anyone can create a group** (`POST /api/groups`) and is its first **admin**. Admin is per group (`appx_group_members.role`): admins invite people, let in people waiting, make others admin or regular, remove people, rename or delete the group, and edit/delete any expense or decide any payment in it. A group always keeps at least one admin. Anyone can leave (`POST …/leave`).
- **Invites by username or email** (`POST /api/groups/:id/members/invite`, admins only). Unknown usernames/emails get "No one on Split It has …". The person sees the invitation on Home (`GET /api/invitations`) and in notifications, and joins only by accepting (`POST /api/groups/:id/invitation/accept|decline`).
- Membership status (`appx_group_members.status`): `active`, `pending` (asked to join, waiting for an admin: `…/members/:id/approve|reject`), `invited`, `removed`. Removed people keep their row so history shows their name.
- **Groups never see each other**: every group route checks the caller is an active member of that group; there is no public group list any more, and group names need not be unique.
- **Linking accounts** (`POST /api/me/link`): someone with two accounts (e.g. one per group from before accounts) proves the other one's PIN; its groups, expenses, shares (added together on the same expense), payments, UPI details and notifications move into this account, payments between the two are dropped, and every other balance stays exactly the same.

### Site owner: General and Admin tabs (migration `0014`)
One account is the site owner (`appx_users.site_role='admin'`): the old administrator, or on a fresh install the first account to enter the admin key at `#/admin`. Only the owner sees **General | Admin** in the header. **General** is their ordinary account (only their own groups). **Admin** is a console opened with the admin key (`ADMIN_PIN`) once per session (12 h, **Lock** ends it): totals, **People** (search) and **Groups** (members, admins, totals, **Reset PIN** clears a group's PIN so its admins can set a new one), never anyone's expenses. The owner can't reset anyone's password. Every `/api/site-admin/*` route is 404 for everyone else.

### Moving existing data to accounts
Migration `0013_accounts.sql` changes no money data. Every existing member becomes an account with the **same id, name and PIN**, so expenses, splits, payments, UPI details and notifications stay attached. Each gets a username of name + random part (e.g. `vicky_3fa2c1`, or `user_…` for names that can't be usernames) and signs in once with **"Used Split It before? Sign in with your group"** (group name + their name + PIN, `POST /api/auth/legacy-signin`), then picks a username in their profile. The old administrator becomes account `admin`, admin of every group they were in and the site owner; they sign in that way once with the **old admin PIN** and choose a 4-digit PIN. After that `ADMIN_PIN` is only the key that opens the Admin tab. Removed members stay out; people waiting for approval stay waiting. The old global Admin area is replaced by the owner's console. `tests/legacy-migration.test.js` builds a database with the previous version of the Worker (`tests/fixtures/legacy/`), applies the migration and checks every balance, debt, expense and payment is unchanged.

## Money and debt model
- All money is stored and computed in integer paise (`*_cents` columns). Amounts are parsed from rupee strings/numbers with at most two decimals (`src/money.js`); exponents, hex, booleans and fractional paise are rejected.
- **Equal split** divides paise exactly; leftover paise go to the first members, so shares differ by at most one paise.
- **Manual split** must add up exactly to the total; duplicates, non-members, negatives, fractional paise and all-zero allocations are rejected server-side.
- **Debts use direct expense attribution** (`src/settlement-logic.js`): for each expense, every split member other than the payer owes their own share to the payer. Edges are summed per pair, repayments are subtracted from the same pair, and opposite directions are netted. The UI shows "You need to pay X" / "X needs to pay you" from this model only; no net-settlement plan is shown.
- Net balance = paid − own shares + repayments made − repayments received. It always equals (owed to you − you owe) over the pairwise debts, and group balances sum to zero.
- Repayments: a normal member can only record a payment from their own account, to an active member, for at most the exact outstanding amount (re-checked atomically inside the INSERT). A group admin can record any payment in the group, including to/from removed members, so those debts can still be cleared.
- **Payments need the receiver's confirmation** (migration `0009`, `appx_settlements.status`). A recorded payment is `pending` and does not count in any balance or debt until the person who received it confirms it (`POST /api/groups/:id/settlements/:sid/confirm`); they can also reject it (`…/reject`, kept for the record, never counts), and the payer can cancel it while pending (`…/cancel`). It counts immediately only when the recorder is the receiver, or a group admin records a payment to someone removed from the group (who can no longer confirm). Pending payments are reserved against the debt, so they can never add up to more than is owed, and confirming re-checks the amount still fits (expenses may have changed). Home and each group show payments waiting for you (`GET /api/payments/pending`); payments made before `0009` stay confirmed.

## Frontend
- React 19 + TypeScript + Tailwind CSS v4 + shadcn/ui (Radix primitives), in `web/`. Built by Vite into `dist/`, which the Worker serves.
- `wrangler.toml` has `[build] command = "npm run build"`, so `wrangler dev` and `wrangler deploy` (including Cloudflare's Git-triggered deploys) build the app first.
- Data: TanStack Query. Every write refreshes the affected screens, and a progress bar under the top bar shows while requests are in flight. Buttons show a spinner and are disabled until the request finishes.
- Look: "Quiet", light only. Near-white paper, white cards with hairlines and a whisper of shadow, ink for actions, neutral monograms and category tiles, and one restrained emerald (money owed to you) / muted rust (money you owe). Outfit (bundled) at light weights; large balances with smaller paise.
- Feel: fluid page and tab transitions, springy pill indicators, count-up amounts (animation features load after first paint), a floating bottom tab bar and ink "Add expense" button in groups, vaul bottom sheets, dark pill toasts, press-scale feedback, a short vibration on Android when a save succeeds.
- Freshness: the Worker serves the HTML with `Cache-Control: no-cache` and hashed `/assets/*` as immutable, so a new deploy shows up on the next open. The account menu and the sign-in screen show "Build <commit> · <time>" so you can confirm which version is live.
- **UPI payment details** (migration `0010`, `appx_payment_methods`, one row per person per kind; only `upi` for now). Each person adds a UPI ID and uploads their UPI QR from the account menu ("Your UPI"); it is stored by their permanent id, so it applies in every group. QR images are shrunk in the browser (≤720 px), then checked on the server by their real bytes (PNG/JPEG/WebP only, ≤300 KB) and served with `nosniff` only to people in the same group (`GET /api/groups/:id/members/:memberId/qr`). The Payments tab lists everyone's UPI ID and QR (`GET /api/groups/:id/payment-methods`), and Settle up shows the receiver's QR, UPI ID and a `upi://pay` link with the amount filled in. Only `/api/payment-method` accepts bodies up to 512 KB; everything else keeps the 16 KB limit.
- **In-app notifications** (migration `0011`, `appx_notifications`). A bell next to the profile circle shows how many are unread; it opens `#/notifications` (newest first, opening marks them read). People hear about: an expense they are in being added/changed/deleted (with what it means for them, e.g. "you owe ₹30"), a payment to confirm, their payment being confirmed/rejected/cancelled or recorded by someone else, being invited to, approved into or made admin of a group, and (admins) someone joining. Nobody is told about their own action. Notes are written in the same batch as the change (`GET /api/notifications`, `POST /api/notifications/read`); notes older than 90 days are cleared, and deleting a group removes its notes. These are in-app only (no phone push yet).
- **Payment approval details** (migration `0012`): a payment can carry a screenshot (`proof` on `POST …/settlements`, checked like QR images, stored in `appx_payment_proofs`, served only within the group at `GET …/settlements/:id/proof`). Until the receiver approves, the payment shows an "⏳ awaiting approval" badge on Home, Balances, the person page and Payments; `/api/balances` returns `waitingOutCents` / `waitingInCents` per person.
- **Phone (push) notifications** (`src/push.js`, `appx_push_subscriptions`): everything that appears on the bell is also pushed to each device the person turned notifications on for (Notifications screen → "Get phone notifications"). Standard Web Push with VAPID (RFC 8292) and aes128gcm encryption (RFC 8291) using WebCrypto only, sent after the response via `ctx.waitUntil`; only real push-service hosts are accepted, devices that report 404/410 are forgotten, and signing out unlinks the device. Android Chrome works in the browser and the installed app; iPhone needs the installed app (iOS 16.4+). It is **off until these Worker secrets exist**: `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` (from `npx web-push generate-vapid-keys`) and `VAPID_SUBJECT` (`mailto:you@example.com`). They are deliberately not in `[secrets] required`, so deploys work without them; for local `wrangler dev`, pass them with `--var` (wrangler only loads the listed secrets from `.dev.vars`).
- Installable app (PWA): `web/public/manifest.webmanifest`, icons in `web/public/icons/`, and a small service worker (`web/public/sw.js`) that always fetches pages fresh and only falls back to the last loaded page when offline (API calls are never cached). "Install the app" on the sign-in screen and "Install app" in the account menu open Chrome's install dialog on Android, and show the Share → Add to Home Screen steps on iPhone (Safari or Chrome). Both are hidden inside the installed app.
- Navigation uses hash routes (`#/`, `#/profile`, `#/notifications`, `#/g/:id`, `#/g/:id/e/:expenseId`, `#/g/:id/p/:memberId`), so the Android back button works.
- Group screen: hero with your position, **Add expense** / **Settle up**, tabs for Expenses (table, tap a row for the split, search, delete), Balances (you and each person → drill-down, group balances, who owes whom), Payments (table) and Insights.
- Person drill-down (`GET /api/groups/:id/with/:memberId`): every shared expense and payment between you and that person with a running balance that ends at the current debt.

## Passwords and PINs
- Account passwords and group PINs are stored only as hashes (`appx_users.pin_hash`, `appx_groups.pin_hash`): PBKDF2-SHA256, 100,000 iterations, a random 16-byte salt each, with `SESSION_SECRET` mixed in as a pepper so a copy of the database alone cannot be brute-forced. **Rotating `SESSION_SECRET` invalidates every password and group PIN.**
- 5 wrong passwords in a row lock that account for 15 minutes (on top of the per-IP sign-in limit); 5 wrong PINs lock that group for that person for 15 minutes.
- Members from before PINs have no password yet: their first sign-in asks them to choose one.
- **Nobody can reset someone else's password** (not group admins, not the site owner). A forgotten password can be recovered only by signing in with Google, if it's connected; otherwise it needs a manual fix in D1.

## Security controls
- `HttpOnly; Secure; SameSite=Lax` cookies; cross-site writes (foreign `Origin`) are refused; JSON bodies are capped at 16 KB; split lists are capped at 100 members.
- D1-backed fixed-window rate limits (migration `0006`): sign-in (all kinds) 20/15 min per IP, sign-up 10/hour per IP, linking 10/hour per account, invites 40/10 min and group writes 20/10 min per admin, expenses 60/10 min and settlements 30/10 min per member. If the table is missing, limits fail open and log an error.
- The old admin PIN (still needed once, for the old administrator's first sign-in) is compared in constant time.

## Migrations
Wrangler applies files in name order and tracks them by name only. `0003_reset_app_data.sql` used to delete all app data; it is now a no-op so it can never wipe a database that had not run it yet. Do **not** rename migration files that may already be applied.

Before applying remotely, check what is pending:

```bash
npx wrangler d1 migrations list split_expense_db --remote
npx wrangler d1 migrations apply split_expense_db --remote
```

## Cloudflare deployment
1. Set production secrets (never commit them): `npx wrangler secret put ADMIN_PIN` and `npx wrangler secret put SESSION_SECRET` (long random value). Rotate them if old values were exposed. Deploys fail with "required secrets have not been set" until both exist.
2. Back up D1 (`npx wrangler d1 export split_expense_db --remote --output backup.sql`), list pending migrations, then apply them.
3. `npx wrangler deploy`, then do read-only checks on the live URL (`GET /api/me` returns `{"user":null}` signed out; load the page and sign in).

The D1 binding is named `split-expense` (see `wrangler.toml`).

## Tests
- `npm test` runs the unit, property, migration and API tests (`node --test`, Node 22+). API tests run the real Worker against an in-memory SQLite D1 double with every migration applied and foreign keys enforced.
- `npm run build` type-checks and builds the web app; `npm run dev:web` runs Vite with the API proxied to a local `wrangler dev` on port 8787.
- `npm run test:e2e` runs a Playwright browser test on a Pixel 7 viewport against a **local** `wrangler dev`. Start it with `npx wrangler d1 migrations apply split_expense_db --local` then `npx wrangler dev --local`, with throwaway `ADMIN_PIN` and `SESSION_SECRET` values in `.dev.vars`. You need Playwright installed. The test refuses to run against a deployed Worker.
